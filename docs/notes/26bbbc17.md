# Card 26bbbc17: Diary of teacher sessions (working notes)

Card: "Add diary functionality that syncs with meditation, coaching and teacher training sessions"
(VibeCodes idea f355ece2, card 26bbbc17-3e42-4df2-8ec0-eba849795adf). Plan step written 18 Nov 2026.
Mock: `docs/notes/26bbbc17-diary-mock.html` (also attached to the card as `diary-tab-mock.html`).

## What Nick asked for
A separate tab with a calendar synced to his Google Calendar, showing his sessions with
Michael Taft, Emily (Horn) and Vince Horn, and the Friday Pragmatic Dharma sessions. Alerts to
meditate before sessions (configurable), a nudge if he hasn't booked one in ages, a count of
sessions, and a way to record a journal entry or a sit after each session, with an alert for it.

Added by Nick mid-plan: say which parts belong in the app and which in Balla Bot. Balla Bot
already reads his calendar, already knows these sessions and already sends 1-hour reminders on
Telegram. Don't give the app its own Google Calendar permission unless there's a strong reason,
and don't duplicate reminders he already gets.

## Decisions taken in the plan (awaiting Nick's approval)
1. **Balla Bot supplies the session list; the app does not get Google Calendar access.**
   Balla Bot already holds a working Google Calendar connection on the same Mac mini, and the
   app already talks to Balla Bot for the teacher (the dharma-llm service on 127.0.0.1:8099,
   bearer token `DHARMA_LLM_TOKEN`). So the cleanest route is one new read-only doorway on that
   same service: `GET /sessions`.
2. **All alerts stay in Balla Bot (Telegram).** The app sends no notifications for this feature.
   Today the app's own reminders only work while a browser tab is open, and they are broken anyway
   (see "Found along the way"). Balla Bot already reaches Nick's phone.
3. **The Diary is for Nick only.** Balla Bot only knows Nick's calendar. The tab shows only for
   emails listed in a new `DIARY_USER_EMAILS` setting. Other invited people see no change.
4. **Matching rules live in Balla Bot**, so "add a teacher" means telling Balla Bot.
5. **Stages:** Stage 1 is Balla Bot's `/sessions` doorway plus the app's Diary tab, counts and
   the write-up/sit links. Stage 2 is Balla Bot-only alert changes. Each ships alone.

## Ruled out, and why
- **App asks Google for calendar permission (adds the calendar scope to Google sign-in).** It
  needs refresh-token storage (Auth.js runs with JWT sessions and no database adapter today, so
  Google tokens are not kept). It means a sensitive-scope consent screen ("unverified app"
  warning). If the Google project is in Testing mode, refresh tokens die every 7 days (not
  checked which mode it is in). And it duplicates what Balla Bot already has. Only worth it if
  other users want the diary.
- **Private iCal ("secret address") link pasted into Settings.** No Google approval needed and it
  would work for any user, but it exposes the whole calendar through one secret link. It also
  needs our own handling of repeating events (the Friday sessions repeat), and it still
  duplicates Balla Bot. Kept as the fallback if the diary ever goes multi-user.
- **App-side alerts (browser notifications, web push, or email).** Browser notifications only
  fire while a tab is open. Web push means new keys, a new service-worker handler and a scheduled
  job, all of which Balla Bot already covers for Nick. It would also double the reminders.
- **Matching on first names.** "Emily" alone wrongly matches unrelated personal events in the real
  calendar (the actual examples are on the board card, not here). Balla Bot's own pre-meeting alerts
  already fire for those. Match on emails and full names only.

## Interface agreed between app and Balla Bot (stage 1)
`GET http://127.0.0.1:8099/sessions?from=<ISO>&to=<ISO>`, header `Authorization: Bearer <DHARMA_LLM_TOKEN>`.
```json
{ "generated_at": "2030-01-01T09:00:00Z",
  "sessions": [
    { "id": "gcal:exampleid0000000000000001",
      "teacher": "Michael Taft",
      "kind": "coaching",              // coaching | mentoring | training_1to1 | group
      "title": "Coaching with Michael Taft",
      "starts_at": "2030-01-02T10:00:00Z",
      "ends_at": "2030-01-02T10:55:00Z",
      "status": "confirmed" }          // confirmed | cancelled
  ] }
```
- Without from/to, it defaults to 2018-01-01 until now + 180 days.
- It returns 401 on a bad token (same rule as /chat) and 503 if the calendar can't be read.
- Balla Bot caches for about 5 minutes. No descriptions, phone numbers, locations or meeting links.
- `id` is stable (Google event id; repeating events use the instance id).
- Write-up links that Balla Bot sends in stage 2 use this id:
  `https://dharma.balla-bot.uk/journal/new?diary=<id>` and `https://dharma.balla-bot.uk/timer?diary=<id>`.

## Build, stage 1 (app side only)

be built on its own card. The app is coded against the interface above and copes with it missing.

### What was built
- `src/lib/diary/`: `access.ts` (who sees the Diary), `source.ts` (asks Balla Bot, 4 s limit, checks
  the reply by hand, never throws), `reconcile.ts` (pure: brings the saved copy in line with a reply),
  `counts.ts` (pure: counts, waiting rule, ordering, wording, UK time), `sync.ts` (runs it against the
  database), `lookup.ts` (finds/links a session for `?diary=` links). Tests in `__tests__/` use a fake
  Balla Bot (fake fetch) and invented data.
- `src/app/(app)/diary/`: page, client layout from the mock, and the two undoable actions.
- Diary button in the nav for `DIARY_USER_EMAILS` only; `/diary` protected and sends others Home.
- Home: one "How did ... go?" line for diary users, from the saved copy only (never asks Balla Bot).
- Journal: `/journal/new?diary=<id>` pre-fills title, tags and a "For your session" line; saving links
  the entry and returns to the Diary. Deleting the entry un-links it (the database does this).
- Timer: `/timer?diary=<id>` shows "After: ..."; the link is kept in the timer's saved state so a
  reload mid-sit keeps it. Saving links the sit (and the notes entry, if the session has none) and
  returns to the Diary.
- Settings: export includes diary sessions; delete-account removes diary rows first and doesn't fail
  if the diary tables aren't there yet.
- `scripts/mini/sql/2026-11-diary.sql`: **not applied**. Checked on a throwaway copy of the schema
  (a scratch database made from a schema-only dump, then dropped): it applies cleanly, a second
  user can't see the first user's rows, and an upsert keeps "didn't happen".

### Decisions made while building, and why
- **One bulk save instead of per-row inserts/updates.** `reconcile` returns `{upserts, markRemoved}`
  (the plan said `{inserts, updates, markRemoved}`). Every session in a reply is saved in one request
  keyed on (user, Balla Bot id), sending only calendar fields, so user choices and links can't be
  overwritten. A first sync back to 2018 would otherwise be ~100 separate requests.
- **No `refreshDiary` server action.** The Diary page already syncs every time it loads, so Refresh
  and Try again just reload the page's data. A server action would have synced twice.
- **A 404 from Balla Bot means "not built yet".** The Diary then says "Balla Bot isn't sharing your
  calendar sessions with the app yet" rather than a generic failure. Same for a missing address or token.
- **Failed links are shown, not hidden.** If an entry or sit saves but can't be linked to its session,
  the Diary opens with a notice saying so (rather than silently showing the session as not done).
- **Saving a linked sit goes to the Diary** (the plan only said this for journal entries), so you see
  it marked straight away. Unlinked sits still go Home as before.
- **First write-up wins.** A second entry for the same session doesn't replace the "Read entry" link.
- **"Before the diary existed"** shows only when the session ended before the diary first saw it;
  otherwise an old un-written session says "Not written up".
- **Month names as in the mock** ("Sep", not "Sept"), so dates are built from en-US parts in UK time.
- **Teachers with equal counts** are ordered by their next session (matches the mock's order).
- **New tables grant only to `authenticated`**, not `anon` as the old tables oddly do.
- **Update policies also have a `with check`**, so a row can't be moved to another user.

### What Balla Bot must provide (its own card)
`GET /sessions?from=<ISO>&to=<ISO>` on the dharma service (127.0.0.1:8099), header
`Authorization: Bearer <DHARMA_LLM_TOKEN>`; reply `{ "generated_at": ..., "sessions": [ {id, teacher,
kind, title, starts_at, ends_at, status} ] }` exactly as in "Interface agreed" above.
- `id` stable (Google event id; instance id for repeats), non-empty. `teacher` non-empty
  (e.g. "Michael Taft", "Vince Horn", "Emily Horn", "Pragmatic Dharma"; the app shows the group as
  "<teacher> teacher training" and tags write-ups with the lower-cased teacher).
- `kind`: coaching | mentoring | training_1to1 | group (anything else shows as "Session").
- `starts_at`/`ends_at`: ISO 8601 in UTC; end not before start. `status`: confirmed | cancelled.
  Rows breaking these are skipped; a reply without a `sessions` list is ignored as a whole.
- 401 for a bad token, 503 if the calendar can't be read, reply within 4 seconds.
- Must cover the whole asked-for window: a future session (or one that started in the last day) missing
  from a reply is treated as cancelled. On the first sync the app asks from 2018-01-01; after that from
  60 days ago; always up to a year ahead.
- No descriptions, phone numbers, locations or meeting links.
